Deliberate design decisions the grader should be aware of:
- Peak grouping. The peaks file contains 15 repeated (chrom, start, end) intervals with different fc values. Collapsing peaks to distinct intervals (the notebook's implicit groupby semantics) yields exactly one row per distinct interval — 40572 distinct intervals, of which 40557 survive trimming, matching the reference row count exactly with no leftover rows. The public spec therefore says "each distinct peak interval P". Any implementation that instead emits one row per peak record would produce 15 extra rows in untrimmed regions, which the comparison stage should reject as a deviation from the public text.
- fc and motif_pval decimal formatting. The exported reference is a pandas float CSV, so fc and motif_pval are emitted with Python float repr ("97.8" not "97.80"; "450.0" not "450"). The oracle copies this convention verbatim (fc from float(field), pval as float()). The controller's comparison rules must compare these fields numerically (or normalize representations), otherwise legitimate scientific answers formatted differently would fail; this is the main remaining validation question for the comparison stage. Row order is already declared free by the approved spec and is genuinely free (the oracle's natural order happens to match, but that should not be graded).
- Row order. Oracle writes peak groups in input-file order (same order as the reference), but the spec explicitly frees row order, so comparison should be order-insensitive on the tuple (chrom, start, end) identity or a row multiset.
- Trimming versus assignment decoupling. Assignment uses the original untrimmed peak span; 1 surviving row (chr17:65556443-65556707, trimmed to 65556624-65556707) carries a motif that no longer overlaps the trimmed span. This is documented in the public text ("Motif assignment is performed on the original, untrimmed peak spans"); the comparison stage should not require the assigned motif to overlap the reported sub-interval.

Leakage considerations: the reference table itself is the answer, so it must never reach the solver; the oracle only reads the three supplied inputs via --input-dir. No hidden caches, no reference answer values embedded, no incidental package naming conventions required (chromosome names are matched as exact strings; no assembly metadata or chrom-size tables are needed because subtraction is implemented per chromosome without a genome view). Off-target contigs in the motif track (e.g. chr11_KI270721v1_random) and odd peak contigs (chrM, chrUn_*, alt/random contigs) are all handled by the same exact-name grouping and are naturally unmatched/blank where appropriate, matching the reference.
