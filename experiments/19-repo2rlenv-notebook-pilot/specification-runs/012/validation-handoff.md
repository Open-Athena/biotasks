Private handoff for the executable validation stage — unresolved questions and dependencies, not acceptance rules.

**Run-to-run repeatability of the pinned recipe (unmeasured).** Only one passing reference run exists. Whether re-running the exact pinned recipe reproduces (a) the same cluster counts at each of the four Leiden resolutions, (b) the same label assignments per cell, and (c) byte-identical CSVs, is unmeasured — UMAP (numba/pynndescent parallelism, init layout) and igraph Leiden have recorded default seeds but their determinism in this environment/threading must be established by repeated execution before any tolerance is fixed.

**Cluster labels are reference conventions, and downstream lookups are label-keyed.** If validation considers accepting a solver whose partitions match up to label permutation: `cell_type_lvl1` is defined by mapping specific `leiden_res_0.02` label strings to lineages, and the DE table's `group` column and the notebook's own interpretive read (cluster 7 → NK via NKG7/GNLY) are label-keyed. A permutation-tolerant rule would require re-keying these lookups, which is an untested transformation — decide, don't assume. Note the group set is itself a computed output (number of leiden_res_0.50 clusters was observed, not assumed): must the solver reproduce the same number of clusters before gene-level comparison is meaningful, and if it differs, what is the intended failure mode?

**Endpoint 1 — `cell_clusters_umap.csv`.** Decide how to compare: exact categorical match for the cluster/tannotation columns vs partition-equivalence; how to treat unannotated (`cell_type_lvl1` blank) cells if a run produces coarsest clusters outside the notebook's 5-key map (the single reference run had none — stability unconfirmed); what tolerance or alignment statistic (if any) applies to `umap_1`/`umap_2`, including UMAP's degenerate global orientation/translation and potential run-to-run drift; whether row order (s1d1 block then s1d3) is part of identity or may be re-sorted by `cell_id`; and whether the `cell_id` suffix convention (anndata `make_index_unique`: first occurrence unchanged, later duplicates `-1`, `-2`, …) is required verbatim, since relabeling changes downstream barcode joins.

**Endpoint 2 — `rank_genes_groups_leiden_res_0.50.csv`.** Decide: equality of the $(group, names)$ pairing set before numeric comparison; tolerance for `scores`/`logfoldchanges` (reference stores these at float32, then CSV-serializes) vs the float64 p-value columns; treatment of exact-zero p-values (raw underflow to 0.0 was observed in the reference export) where relative tolerances are undefined; whether the flattened block/rank ordering (category order = natural-sorted labels; per-block rank order) must match exactly or only row identity by keys; and how ties and near-equal scores at adjacent ranks are handled. Also decide the minimum meaningful extent (top-k per group vs full table) — the notebook only interprets the top of each ranking.

**Endpoint dependence across outputs.** The DE group set/block sizes must reconcile with `leiden_res_0.50` in endpoint 1, and `names` must live in the same uniquified gene-symbol space; validation must decide whether these are checked jointly and what to do on a gene-identifier mismatch caused by a different uniquification convention.

**Endpoint 3 — `params.json`.** Whether this is compared as an exact key/value set (it records source-determined values, including `use_raw: false`, which follows from the notebook never setting `adata.raw`) and whether `layer: null` serialization is required verbatim.

**Representation vs newly computed results.** The dendrogram in `uns['dendrogram_leiden_res_0.50']` is computed inside a plotting call (defaults) — confirm no endpoint depends on it; similarly the Leiden `uns` modularity scores and scrublet outputs are intentionally outside the deliverables. If any alternative implementation is to be accepted (not promised), its numeric agreement must be measured before it is allowed.

**Resource/timing.** Reference run: 147.5 s, peak child RSS ~5.05 GiB (solitary-process measure). Confirm solver-side feasibility under the provisional 600 s / 8 GiB limits and decide the timeout before release; reference runtime does not establish solver runtime.
