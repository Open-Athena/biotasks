## Coverage

The original source (`inputs/original.py`) is a standard scanpy bone-marrow scRNA preprocessing + clustering tutorial with two terminal branches: (i) clustering/annotation (Leiden at default + 3 resolutions, manual cell-type map from the coarsest solution, UMAP embedding), and (ii) per-cluster DE genes at resolution 0.50 (Wilcoxon vs rest). Both terminal branches are captured by the plan, and no other independent terminal results exist at completion:

- QC metrics, scrublet doublet scores, HVG annotations, PCA and the counts/log1p layers are intermediates/diagnostics (correctly excluded per role); none is re-filtered further after computation in the source.
- `dc_cluster_genes` is a top-5 view of the cluster-7 ranking, fully contained in endpoint 2; the follow-up plot consumes it only internally.
- The `marker_genes` dict is prior-knowledge input consumed by dotplots, not a computed result.
- The only last-written-value subtleties are the assignments to `adata.obs[...]` keys, which are cumulative (no overwriting; `leiden` is written once by the default-resolution call and the three resolution-loop keys are distinct via `key_added`). No eligible terminal result is overwritten.

The adaptation (`candidate/analysis.py` vs `trial/source.diff`) changes only: (1) XDG_CACHE_HOME/backend (environment), and (2) `load_registry_from_doi()` → `load_registry(staged registry.txt)` (network staging). Both preserve the scientific content; `pooch` 1.9.0 `load_registry` (core.py:634-683) takes `name hash [url]` lines, and `os_cache()` (utils.py:77-89) honors `XDG_CACHE_HOME`, so the staged cache + registry reproduces the online behavior with identical md5 verification. The two 10x h5 files are byte-verified against provider md5s in the setup log, so input identity is preserved. The exports (`inputs/exports.py`) only serialize existing values (`adata.obs` subset, `obsm['X_umap']`, `uns['rank_genes_groups']['names'/'scores'/'pvals_adj'/'pvals'/'logfoldchanges']` group-by-group, `params`), with no recomputation, filtering or re-ranking.

## Fidelity findings from pinned-source inspection (installed versions)

- `sc.tl.leiden` (scanpy 1.12.4, `scanpy/tools/_leiden.py`): the main call (`flavor="igraph", n_iterations=2`) and the resolution-loop calls (`flavor="igraph"`, `n_iterations` omitted) are *different operations* — the loop inherits the default `n_iterations=-1` (run until optimal), not 2. Both use `igraph.Graph.community_leiden` with `objective_function="modularity"`, edge `weights="weight"` (only when `use_weights=True`, the default), undirected graph, `random_state=0` (via `set_igraph_random_state`), `resolution∈{0.02,0.5,2.0}`. The brief must keep this asymmetry; the plan's descriptions do not contradict it but do not state it.
- `sc.pp.neighbors(adata)` runs with `n_neighbors=15, n_pcs=None, use_rep=None, knn=True, method="umap", metric="euclidean", random_state=0`; `_choose_representation` resolves to the full `X_pca` (all 50 components) because n_vars > 50 and no `n_pcs` is given (`scanpy/tools/_utils.py:41-64`). Since n_obs = 17,041 > 4096, the kNN backend is `pynndescent` (with UMAP-like `n_trees`/`n_iters`), not brute-force sklearn (`scanpy/neighbors/__init__.py:733-788`).
- `sc.tl.pca(adata)`: `n_comps=None` → `settings.N_PCS` = 50; `_handle_mask_var` (`scanpy/preprocessing/_pca/__init__.py:431-437`) auto-selects `mask_var="highly_variable"` because `highly_variable` is in `adata.var.columns` after `pp.highly_variable_genes`; default dense/sparse solver is `'arpack'`. PCA is therefore computed on the 2000 HVGs, not on all genes.
- `sc.pp.highly_variable_genes(adata, n_top_genes=2000, batch_key="sample")`: default `flavor="seurat"` with the given cutoffs ignored when `n_top_genes` is set (per docstring lines 708-718); batch-key mode selects per-batch then merges (nbatches ordering).
- `sc.pp.normalize_total(adata)`: `target_sum=None` → median-of-total-counts normalization (per-cell to median across all cells; `scanpy/preprocessing/_normalization.py:174-177`).
- `sc.pp.scrublet(adata, batch_key="sample")`: per-`scanpy/preprocessing/_scrublet/__init__.py:262-304`, runs independently per sample on a copy with internal `filter_genes(min_cells=3)`/`filter_cells(min_genes=3)`, its own normalize_total/CPM and HVG selection, `n_prin_comps=30`, `sim_doublet_ratio=2.0`, `random_state=0`, then maps `doublet_score`/`predicted_doublet` back by position. This confirms it does not mutate the main `.X`/`.var` state (results land on `adata.obs`), and explains the `predicted_doublet` naming in the source re-assessment plot.
- `sc.tl.rank_genes_groups(adata, groupby="leiden_res_0.50", method="wilcoxon")`: `reference="rest"`, `groups="all"` (order from `select_groups`, i.e. categorical `cat.categories` — here "0".."16" string categories), `n_genes=None` → all genes (≈24 k per group, giving 398,259 rows across 17 groups); `corr_method="benjamini-hochberg"`; `use_raw` resolves to `False` because `adata.raw` is empty (`_rank_genes_groups.py:786-790`); dtypes are `names:object, scores:float32, logfoldchanges:float32, pvals:float64, pvals_adj:float64` (`_rank_genes_groups.py:888-899`), which matches the observed CSV (float32 rounding visible in `scores`, e.g. "85.90431"). The observed export is a faithful flattening of these struct arrays.
- `ad.concat(adatas, label="sample")` (anndata 0.13.4, `_core/merge.py:1440-1453`): `join=Default("inner")` resolves to the intersection of variables across the two samples, `index_unique=None` keeps raw indices until `obs_names_make_unique()` appends `-1/-2/...` to duplicate barcodes. This defines cell_id identities in endpoint 1.
- `sc.read_10x_h5`: `gex_only=True` (default) keeps only Gene Expression features; each sample's `var_names_make_unique()` is applied before concat. The setup log's "Variable names are not unique" warnings are from the read-copy path, expected and non-effectual.

## Execution/audit consistency

- One passing reference run (147.5 s, peak RSS ~5.0 GiB, within 600 s / 8 GiB policy) produced all three declared artifacts; both h5 inputs were md5-verified at staging.
- Observed structural facts match the recipes: 17,041 cells (8,785+8,340 raw minus permissive-filtering losses), `leiden` 0-24 (25 clusters), `leiden_res_0.02` 0-4, `leiden_res_0.50` 0-16, `leiden_res_2.00` 0-35, all-mapped `cell_type_lvl1`, 398,259 DE rows = 17 groups × genes tested (23,427 per group median, consistent with n_genes=None → all genes on the inner-join var set). `rank_genes_groups_params.json` matches the pinned defaults exactly.
- The audit only previews/summarizes; it does not claim full verification, and semantic fidelity is explicitly unvalidated. This does not block drafting — comparison rules/tolerances are the next stage's responsibility.

## Uncertainties (not blockers)

- Solver-side variability of UMAP/Leiden/n_neighbors components across implementations/versions is expected; the brief pins the reference conventions but must not promise cross-implementation equality (it doesn't).
- Exact `leiden`/`leiden_res_*` cluster counts depend on igraph 1.0.0's Leiden implementation under `random_state=0`, `n_iterations=2` or `-1`; a fixed seed alone does not prove stable results across platforms/builds — flagged in the handoff instead of the brief.
- `rank_genes_groups` group ordering follows the `leiden_res_0.50` categorical ordering (natsorted "0","1",...,"16" written by `sc.tl.leiden`, `_leiden.py:195-198`), not insertion order — stated in the brief since it defines row identities of endpoint 2.

No source contradictions, no missing evidence preventing a faithful recipe draft, no export/science defects found.
