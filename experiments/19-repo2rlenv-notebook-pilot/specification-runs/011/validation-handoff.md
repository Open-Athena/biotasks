1. **Stochastic cross-implementation stability**: the reference UMAP (umap-learn 0.5.12, spectral init, random_state=0, n_epochs=200 for >10k cells), pynndescent kNN, and igraph community_leiden (igraph 1.0.0) runs are deterministic under the pinned builds but a fixed seed does not guarantee identical results across builds/libraries. Validation must decide: exact-match vs tolerance-based comparison; whether UMAP coordinates are compared up to global translation/reflection/isotropic scaling; whether cluster labels are compared up to permutation (relabeling invariant) or including the source-defined label strings (required for `cell_type_lvl1`, since the map is keyed on `leiden_res_0.02` labels — a permuted labeling breaks the map and is NOT a pure representation change). Positive/negative controls needed: label-permutation sensitivity, reference rerun for repeatability.
2. **Same-seed rerun repeatability**: the evidence includes only one passing run. A repeat run of the reference is needed to establish whether leiden/UMAP outputs are exactly reproducible under the pinned versions before exact-match grading is offered.
3. **Cluster-count sensitivity**: `leiden` 0-24 (25 clusters), `leiden_res_0.50` 0-16 (17 groups) drive the DE table's shape and the manual cell-type map. If counts shift under any acceptable variation, the exported DE table row count and the `leiden_res_0.02 → cell_type_lvl1` mapping validity change. Validation must decide whether cluster counts are fixed acceptance criteria or only the downstream tables are compared.
4. **Endpoint 2 comparison questions**: (a) confirm group order follows `cat.categories` (natsorted "0".."16") rather than any other order; (b) rank order within group (descending `scores`) including negative-score entries — decide whether tail rows are compared exactly or only top-k; (c) float32 `scores`/`logfoldchanges` vs float64 `pvals` indicate precision limits (~7 decimal digits) — set numeric tolerance accordingly; (d) ties/critical p-values at 0.0 after BH correction may differ in the last digits across platforms;
 (e) the 398,259-row count should be verified as 17 groups × the full var set (23,427 genes per group median) — confirm the exact inner-join var count from the source data; the number is not independently reproduced in the audit.
5. **Cell-id identity rule**: barcodes are made unique only for duplicates **across** samples (suffix `-1`/`-2`). Validation must confirm this rule from the source data (which barcodes repeat) so a solver cannot float a different suffix convention; also confirm `sample` values (`s1d1`/`s1d3`) are taken verbatim.
6. **Cross-output dependency**: endpoint 1's `leiden_res_0.50` column and endpoint 2's `group` values must refer to the same clustering solution; validation should include a cross-check (group sizes per cluster from output 1 vs rows per group in output 2, and DE run params from output 3 matching the groupby/method used).
7. **`rank_genes_groups_params.json` representation**: reference writes `layer: null` and `use_raw: false` (JSON `null`/`false`); confirm the exact JSON shape (indentation 2, `default=str` no-op) is a formatting-only requirement or only content is graded.
8. **UMAP/Leiden negative controls**: validation should verify a failing alternative (e.g., different number of PCs, non-HVG PCA, or resolution change) is distinguishable under the chosen tolerances — i.e., the contract is not so loose that scientifically different clusterings pass.
