## Comparison rules (proposed, not validated)

**LuxC.domtbl (primary semantic endpoint)**
- Normalize: strip the 3 leading `#` comment lines; verify remaining rows form the reported hit set with one row per reported domain.
- Row order encodes rank: compare the ordered list of target names first (order-sensitive rank comparison). Both replays were byte-identical; ordering by full-sequence E-value ascending is the scientific ranking. If a solver library uses a different tiebreak among equal E-values (not expected here; all 12 targets have distinct E-values in the reference), the validator should check for exhaustiveness of the rank ordering rather than force one deterministic tiebreak.
- Identities: target name/accession, tlen, query name/accession, qlen, hmm/ali/env coordinates, domain number-of counts, acc — compare exactly as strings/integers.
- Numbers: E-values (both full-sequence and per-domain), bit scores, bias values — compare within a relative tolerance to be calibrated by executable validation. Proposed: parse scientific-notation E-values to float, require `|x-y| <= max(rel_tol_i * max(|x|,|y|), abs_floor_i)` with rel_tol_i and abs_floor_i measured from acceptable vs. unacceptable solutions before being finalized (no numeric tolerance is asserted in the public brief yet).
- Explicitly fail (not tolerance-absorbed): a missing/extra target row (different hit set = different scientific result, since reporting thresholds and E-value calibration decide inclusion), a different domain envelope/alignment boundary, a different target length, a wrongly carried query accession (must be PF05893.5, which derives from the input alignment's `#=GF AC` — solver must carry MSA annotation to HMM, which hmmbuild does by default).
- Row permutation probe: not applicable (rank order is scientific meaning, not serialization accident).

**LuxC.hmm (dependent endpoint, upstream of domtbl)**
- Normalize: drop `DATE  ...` and `COM   ...` lines (run-variant). Keep everything else.
- Compare header block (NAME, ACC, DESC, LENG, ALPH, flags, NSEQ, EFFN, CKSUM, GA/TC/NC, STATS lines) — structural key: NAME must be LuxC, ACC must be PF05893.5, LENG = the number of match columns (400 for this input), EFFN and STATS are calibration-derived floats → tolerance, CKSUM is a checksum (skip or tolerance). GA/TC/NC must equal the MSA-annotated cutoffs exactly (integer-like floats carried verbatim).
- Model body: 400 model positions; per-position emission scores, insert emission scores, and 7 transition scores. For the same engine (pyhmmer 0.12.3) these are expected byte-identical; for an alternate HMMER3-compatible implementation propose comparing within a small absolute tolerance per entry (e.g., differences in log-odds emission scores at the third decimal or beyond). Calibrate with a deliberately wrong run (e.g., builder with weighting="none" or symfrac=0.6) to confirm the comparison catches real scientific deviations — measurement not yet made.
- Cross-output dependency: HMM LENG/NSEQ fields must be consistent with the domtbl's qlen and the query name/accession; the exact built HMM determines the domtbl values. A valid alternative HMM that still reproduces the domtbl within tolerance should not be byte-compared strictly.

## Incorrect-output probes to run during validation

1. `hmmbuild` with `--wpb` vs correct default: confirm the reference is the default run. (Already established from source; no test needed.)
2. Build with non-default weighting (`--wnone`) and re-search: should yield a materially different domtbl or HMM body; verify the grader fails it.
3. Truncate/extend the reported hit set (e.g., E=1 instead of E=10, or `--cut_ga`): should fail the domtbl row-set check; confirms bit_cutoffs=None matters.
4. Re-run the whole pipeline with a different RNG mechanism affecting calibration (e.g., `--seed 0`): confirm the domtbl and HMM body still fall within tolerance (calibration should be deterministic-stable across engines' simulation conventions — this is the key portability assumption to validate).
5. Row-permutation probe on domtbl: reorder rows and confirm the grader handles rank-relevant ordering vs. pure re-serialization. Reorder only domains within one sequence if the case arises; here each sequence reports one domain, so per-sequence row order is the only rank information.
