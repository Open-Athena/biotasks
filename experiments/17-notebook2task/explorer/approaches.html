How notebooks become tasks

Two published approaches, followed by the notebooks and task evidence we are inspecting. Authoring a task and solving it are separate stages.

SETA

Inspected Kaggle-notebook pathway · released prompts

  1. 01 · SourceKaggle notebook + local datasets

    Metadata, dataset manifests and a cell-by-cell notebook outline are preloaded. The authoring agent can read the original notebook for details.

  2. 02 · Specification authoringSeed → task specification

    A viability check can reject the seed. Otherwise the agent designs a terminal task around the analysis objective and writes a draft specification.

  3. 03 · Task constructionSpecification → Harbor package

    Produces instructions, environment, reference solution and executable tests. The builder prompt requires preflight checks, including reference success and empty-submission failure.

  4. 04 · Solver and gradingFresh attempt → artifact checks

    The solver works from task instructions and staged inputs. The reference solution and verifier are separate assets; this pathway asks the solver to solve the problem using its own approach.

Inputs, review and limits

Does the authoring model see the notebook? Yes: a preloaded outline and tool access to the notebook when present.

Review: the inspected builder guide specifies model self-review and execution checks. It does not establish a mandatory human-review step equivalent to BixBench’s expert question review.

Scope: this is one released SETA pathway, not every SETA source adapter. Its model-comparison and CPU constraints can reject otherwise useful biology analyses. Prompt requirements do not prove that every released task passed those checks.

Our evidence: released prompts and a cytopathology task are available here. Our GLM authoring experiments and repaired variant are separate from reproducing SETA’s full pipeline.

__SETA_PROMPTS__

Agreed limitations of this recipe

Scope: the pinned Kaggle adapter and shared prompt at 5868a1b, not SETA as a whole. These are observed prompt restrictions and our assessment of their limitations.

  1. Conflicting training instructions. The Kaggle adapter requires multiple trained models; the shared idea-agent instructions prohibit model training. This is a confirmed inconsistency between prompt components.

    Proposed recipe change: Make the permitted computation explicit and consistent across components.

  2. Model-count gate. The adapter rejects a notebook with only one trained model and expects two or more. Model count is a weak proxy for meaningful analytical decisions and restricts coverage of non-training workflows.

    Proposed recipe change: Assess analytical decisions and verifiable outputs without a minimum model count.

  3. EDA-only rejection. The early-ditch examples treat EDA-only notebooks as lacking a clear objective. Exploratory analysis can still yield an assessable task; an actually undefined objective remains a valid reason to reject or refine it.

    Proposed recipe change: Extract an analytical question and required evidence; verify calculations, reproducibility and support for conclusions.

  4. Modality and keyword exclusions. The initial gate rejects mentions of deep learning, neural networks, GPUs, transformers, images, audio or video. Such labels do not establish the resources needed for the task extracted from the notebook.

    Proposed recipe change: Assess the proposed computation and dependencies directly, including CPU analysis of saved predictions, embeddings or images.

Evidence boundary: existing pilots record a multiple-model rejection and training-instruction conflict, but aggregate rejection rates and causal effects on generation quality have not been measured. Proposed changes are not validated improvements.

CPU/resource budgets remain deliberate execution constraints. Local data and lack of browser/search are not classified here as established limitations; “internet disabled” would overstate the inspected instructions.

BixBench

Original paper’s workflow · expert-prepared capsules

  1. 01 · Human analystStudy or new analysis → capsule

    An expert prepares a Colab notebook, input data, hypothesis and result. A prior public notebook is not required.

  2. 02 · Authoring modelReference notebook → questions

    Claude 3.5 Sonnet receives a modified notebook, hypothesis and result, then drafts eight multiple-choice questions.

  3. 03 · Human reviewReview, edit and deduplicate

    Experts inspect questions with the source capsule available. Model-assisted duplicate detection is followed by human verification.

  4. 04 · Solver and gradingData + questions → fresh analysis

    The solver receives an empty notebook, data and questions—not the reference notebook. Open answers are compared with reference answers by an LLM judge.

Inputs, review and limits

Unknown: the precise notebook modification is unresolved in our inspection; an equivalent released authoring prompt has not been identified.

Our example: ASXL1’s underlying study is known; its original code format is not. Our Harbor/Pi attempt uses a terminal rather than the paper’s notebook agent.

Question-generation prompt

Exact prompt not located in the inspected public sources. The paper describes a specially crafted prompt combined with a modified notebook, hypothesis and result. We cannot show the exact generation message or precisely identify which notebook cells/outputs were included.

The public prompts.py contains answering, answer-selection and grading prompts. These serve evaluation, not notebook-to-question authoring. The paper’s appendix also gives a solver initiation prompt. None is substituted here for the missing authoring prompt.

What the authoring request contains

Documented inputs: a modified reference notebook, the capsule hypothesis and result, and generation instructions. The paper identifies Claude 3.5 Sonnet (20241022) as the question author.

Documented output: two rounds of four multiple-choice drafts. Each round asks for one question centered on the hypothesis. Experts may edit, approve or reject drafts with the full capsule available; duplicate candidates are checked by a model and then humans.

Boundary: this is a description of the paper’s procedure, not a reconstructed prompt. The released benchmark questions and answers are artifacts of that process. Our GLM solver attempt does not reproduce the authoring stage.

Notebook provenance for our example

The ASXL1 notebook was prepared in a FutureHouse capsule template using an earlier published study and its data. The study describes an in-house analysis pipeline; we have not established whether its original code was a notebook, scripts or another format. “BixBench source notebook” therefore means the notebook used to make the benchmark questions, not necessarily the original research notebook.

What to compare here: SETA’s inspected pathway builds an executable task package; BixBench’s paper describes generating reviewed questions from expert analyses. In both, notebook access during authoring is different from the inputs given to a fresh solver.
