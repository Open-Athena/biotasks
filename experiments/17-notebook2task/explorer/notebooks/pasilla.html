How notebooks become tasks

Two published approaches, followed by the notebooks and task evidence we are inspecting. Authoring a task and solving it are separate stages.

SETA

Inspected Kaggle-notebook pathway · released prompts

  1. 01 · SourceKaggle notebook + local datasets

    Metadata, dataset manifests and a cell-by-cell notebook outline are preloaded. The authoring agent can read the original notebook for details.

  2. 02 · Authoring modelSeed → task specification

    A viability check can reject the seed. Otherwise the agent designs a terminal task around the analysis objective and writes a draft specification.

  3. 03 · Construction modelSpecification → Harbor package

    Produces instructions, environment, reference solution and executable tests. The builder prompt requires preflight checks, including reference success and empty-submission failure.

  4. 04 · Solver and gradingFresh attempt → artifact checks

    The solver works from task instructions and staged inputs. The reference solution and verifier are separate assets; this pathway asks the solver to solve the problem using its own approach.

Inputs, review and limits

Does the authoring model see the notebook? Yes: a preloaded outline and tool access to the notebook when present.

Review: the inspected builder guide specifies model self-review and execution checks. It does not establish a mandatory human-review step equivalent to BixBench’s expert question review.

Scope: this is one released SETA pathway, not every SETA source adapter. Its model-comparison and CPU constraints can reject otherwise useful biology analyses. Prompt requirements do not prove that every released task passed those checks.

Our evidence: released prompts and a cytopathology task are available here. Our GLM authoring experiments and repaired variant are separate from reproducing SETA’s full pipeline.

BixBench

Original paper’s workflow · expert-prepared capsules

  1. 01 · Human analystStudy or new analysis → capsule

    An expert prepares a Colab notebook, input data, hypothesis and result. A prior public notebook is not required.

  2. 02 · Authoring modelReference notebook → questions

    Claude 3.5 Sonnet receives a modified notebook, hypothesis and result, then drafts eight multiple-choice questions.

  3. 03 · Human reviewReview, edit and deduplicate

    Experts inspect questions with the source capsule available. Model-assisted duplicate detection is followed by human verification.

  4. 04 · Solver and gradingData + questions → fresh analysis

    The solver receives an empty notebook, data and questions—not the reference notebook. Open answers are compared with reference answers by an LLM judge.

Inputs, review and limits

Unknown: the precise notebook modification is unresolved in our inspection; an equivalent released authoring prompt has not been identified.

Our example: ASXL1’s underlying study is known; its original code format is not. Our Harbor/Pi attempt uses a terminal rather than the paper’s notebook agent.

Scope and evidence

This is a purposive collection, not a popularity ranking or a set of independent studies. SETA and BixBench examples remain comparison material and are marked separately from candidate sources. A scientific dataset's benchmark origin alone does not imply overlap with an LLM evaluation.

One parent-reviewed GLM recipe has native CPU validation after a recorded grader repair. Docker/Harbor execution and independent solver evaluation remain untested. Other entries retain their own discovery and authoring status. Original documentation may require internet; the BixBench notebook and bedtools tutorial are bundled reading views.
